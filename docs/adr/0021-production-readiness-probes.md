# ADR-0021：生产就绪探测使用真实直接依赖

- 状态：Accepted
- 日期：2026-08-10

## 决策

核心 API 的 `/health/live` 只回答进程是否存活；`/health/ready` 则必须实际查询数据库并检查当前对象存储桶是否可访问。任一直接依赖不可用时，就绪接口返回 `503`，同时以不包含地址或凭据的受限摘要说明失败依赖。

推理网关继续聚合 API 与推理运行时的就绪状态；推理运行时继续报告模型缓存与可用容量。Worker 的租约、额度预留和 Webhook 恢复任务由独立的 Celery Beat 周期触发，不把“无法直接探测的队列消费者”伪装为 API 已验证的依赖。

## 原因

之前 API 的就绪接口仅代表进程可响应，不能识别数据库连接或对象存储故障。将存活和就绪拆开，使容器编排、负载均衡和人工值守使用同一条可验证事实，同时不增加监控平台、Kubernetes 或消息总线。

## 运行与恢复边界

- PostgreSQL 与对象存储必须采用独立持久卷或托管服务；应用容器及推理缓存卷不是备份来源。
- 每次生产变更前须验证数据库逻辑备份可还原到隔离环境，并抽样验证对象清单、模型产物和能力/工作流规格可读取。
- 恢复先在隔离环境演练，再切换生产流量；不得对来源或范围不明的数据库执行覆盖恢复。
- 初期由部署平台的健康检查、日志与值守告警消费这些就绪结果；阈值、通知渠道和 RPO/RTO 待首发客户与地域确定后固化。
