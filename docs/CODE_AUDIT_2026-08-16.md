# SenseMu 架构与代码审计（2026-08-18）

## 结论

当前代码已经形成可运行、可追溯的视觉算法闭环骨架，产品一级结构也已收敛为“工作台 / 算法市场 / 数据市场 / 我的”。现阶段最重要的不是继续增加页面，而是把本地闭环推进为可部署、可鉴权、可观测、可恢复的生产系统。

Ultralytics Platform 值得借鉴的是对象式工作台、侧栏资源树和就近操作。SenseMu 已吸收这些交互原则，但不会照搬其一级信息架构：市场、供需双方账户、订单与计费仍是 SenseMu 自己的产品边界。

## 审计范围

- 产品：四个一级页面、项目内数据与标注、训练、发布与调用、市场和账户。
- 前端：React 客户端状态、API 调用、响应式布局、可访问性、构建与依赖。
- 后端：Core API、Worker、推理网关、推理运行时、租户与凭据边界。
- 工程：测试门禁、依赖漏洞、配置、文档和可维护性。

本次审计基于当前仓库和本地运行环境；尚无正式 Linux x86/GPU 服务器，因此性能、容量、容灾和生产网络结论仍待真实环境验证。

## 本轮已经修复

### P0 接口与运行稳定性

1. Core API 的浏览器跨域预检已覆盖真实写操作：允许 `GET / POST / PUT / PATCH / DELETE / OPTIONS`，并增加 `PUT`、`DELETE` 回归测试。
2. Web 到 Core API、对象产物和推理网关的请求已加入分级超时与明确错误提示，避免服务失联后页面无限等待。
3. 发布与调用页的页签容器改为正确的可访问性结构，避免 `nav + tablist` 语义冲突。
4. Python 中已弃用的 `HTTP_422_UNPROCESSABLE_ENTITY` 已替换为当前常量。
5. 所有会安排后台执行的任务与 Webhook 写接口均先提交持久化记录，再派发消息；失联租约恢复也先提交重新入队状态，避免 Worker 或投递器读到未提交对象。

### P0 工程质量

1. `make check` 现在包含 Web ESLint，不再只检查构建、类型和后端。
2. Web 生产依赖与开发工具链已升级；npm 完整依赖审计由 17 个漏洞降为 0。
3. 全量检查结果：Web 常规渲染测试 15/15、托管演示回归测试 1/1、Python 测试 89/89、TypeScript、ESLint、Ruff 和 Python 编译均通过。
4. 已清理 13 条 React Hooks 与图片加载警告：异步选择、轮询与健康检查改为稳定依赖；仅对 Blob/鉴权产物图片封装了带原因说明的原生图片组件，不全局关闭规则。
5. Vite 原生配置警告已修复：JSON 导入明确声明类型，站点插件使用显式扩展名，并在 TypeScript 中允许该配置导入。

### 产品交互

1. 侧栏开关已移动到内容顶栏左侧，使用统一的面板图标。
2. 侧栏收起时点击“数据与标注 / 训练 / 发布”，会先展开侧栏和对应资源组，不会直接跳到用户看不见上下文的页面。
3. 桌面和 480px 窄屏均已验证，无新增横向溢出。

## 仍需按优先级推进

### P0：上线前必须完成

1. **真实登录闭环**：后端已有 OIDC 校验和工作区授权，但 Web 尚未完成正式登录、令牌刷新、退出和会话失效处理。
2. **浏览器端到端测试**：已覆盖托管演示的数据、标注、训练报告、实时分析、市场筛选与窄屏响应式布局；隔离的真实写入 E2E 覆盖上传、标注保存、冻结版本、训练创建、发布和密钥一次性展示，并已纳入 CI。下一步只补充服务失联、恢复与权限拒绝等失败路径。
3. **生产数据设施**：在有服务器后，用 PostgreSQL、对象存储和 Redis 完成迁移、备份、恢复、滚动升级及故障演练。

已完成：Core API、Worker、推理网关和推理运行时已在 `staging/production` 阶段拒绝本地默认凭据；Core API 同时拒绝开发身份模式与不完整 OIDC，Worker 拒绝跨架构转译。部署流水线仍需显式注入环境标识和正式密钥。

### P1：首批客户前完成

1. 在原生 Linux x86/GPU 环境复现“训练 → 独立验收 → 发布 → 在线推理”，替换本地宽松 Smoke Test 门禁，并记录训练耗时、P50/P95 延迟、并发和失败恢复基线。
2. 从 OpenAPI 生成前端客户端或至少生成共享类型，逐步替代约 1,600 行手写 `catalog-api.ts`，降低接口漂移风险。已生成可提交 OpenAPI 快照和 TypeScript 类型，并在 CI 校验；调用封装将按业务页面逐段迁移，不进行一次性重写。
3. 拆分高风险大文件：`globals.css` 约 15,000 行，数据工作台、发布工作台、市场服务和应用外壳均超过 900 行。按业务模块拆分，不新增无意义的通用组件层。
4. 固定可复现的 Node/npm 构建环境，并将其接入持续集成。已固定 Node 24.19.0，仓库与 CI 共用 `.nvmrc`，安装、开发、构建、类型和 Lint 检查会提前拒绝错误主版本。
5. 接入成熟标注工具的 YOLO/COCO 交换与人工审核回写；不继续扩展自研通用标注器。

### P2：业务条件明确后推进

1. 选择首个多模态模型供应商后，再实现服务端适配器、加密凭据、超时、重试、审计和计量。
2. 视频流在完成加密地址引用、网络白名单、采样 Worker、断流恢复和旧任务回写保护后开放。
3. 首发地区、签约主体和渠道明确后，再接入支付、KYC/KYB、结算、提现和税务，不在核心代码中提前绑定供应商。

## 代码维护边界

- 保留模块化单体，不在没有真实容量证据时拆微服务或引入 Kubernetes。
- 标注、训练、独立验收、发布和推理继续保持不可越过的事实边界。
- 内部批处理、公网推理、市场计费与供应方凭据保持隔离。
- Mock 只用于演示界面，必须明确标识，不能写入真实指标、验收或账务事实。
