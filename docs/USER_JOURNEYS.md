# SenseMu 用户旅程与业务链路

- 更新日期：2026-08-25
- 面向对象：产品、后端、前端、算法、运营、测试和合作方
- 相关文档：`DEVELOPER_HANDOFF.md`、`PRODUCT_FUNCTIONS.md`、`API_GUIDE.md`

本文梳理 SenseMu 中所有主要参与者的目标、入口、动作、系统事实、成功出口和失败出口。

业务身份与工作区权限是两套不同概念：一个账号可以同时是算法生产者、数据销售者和算法需求者，但在具体工作区内仍可能只有 `viewer` 或 `member` 权限。

## 1. 两层角色模型

### 1.1 业务身份

| 业务身份 | 核心目标 | 主要入口 | 主要产物 |
|---|---|---|---|
| 算法生产者 | 把模型变成可验收、可发布的视觉能力 | 工作台 / 训练 / 发布 | `ModelVersion`、`Deployment`、`CapabilitySpec` |
| 算法销售者 | 把已验证能力变成可发现、可订阅商品 | 我的 / 创作与销售 | `MarketplaceListing`、订单、收入事实 |
| 数据生产者 | 把原始素材变成有来源、有标注、有质量快照的数据版本 | 工作台 / 数据与标注 | `DatasetVersion`、质量报告 |
| 数据销售者 | 在权利和许可明确后发布可交付数据卡 | 我的 / 创作与销售、数据市场 | `DataListing`、`DataDeliverySpec` |
| 算法需求者 | 找到适用算法并完成授权后调用 | 算法市场、我的 / 购买与使用 | `Entitlement`、API Key、`UsageRecord` |
| 数据需求者 | 找到满足用途和质量要求的数据并在授权后接收 | 数据市场、我的 / 购买与使用 | 数据订单、交付任务 |
| 工作区协作者 | 在被授权的工作区内执行生产任务 | 工作台 | 标注、划分、训练任务、审核意见 |
| 平台治理者 | 维护审核、支付、交付、风控和可靠性 | 内部控制面 | 审核、支付、对账、审计事实 |

### 1.2 工作区权限

| 权限 | 读取工作区 | 数据/标注/训练 | 发布与密钥 | 商品/数据卡 | 成员管理 |
|---|---:|---:|---:|---:|---:|
| `viewer` | 是 | 否 | 否 | 否 | 否 |
| `member` | 是 | 是 | 否 | 否 | 否 |
| `admin` | 是 | 是 | 是 | 是 | 是（不含授予 admin） |
| `owner` | 是 | 是 | 是 | 是 | 是，包括管理员角色 |

所有对象都必须由服务端复核 `workspace_id`、成员关系和最低角色，不能只相信 URL 中的 ID 或浏览器传入的工作区头。

## 2. 统一价值链

SenseMu 的主价值不是“上传后直接调用”，而是把每一步变成可追溯事实：

```text
发现问题 → 建立工作区/项目 → 准备数据 → 标注与审核 → 冻结数据版本
→ 训练模型 → 独立验收 → 发布服务 → 固化能力契约 → 审核上架
→ 下单/授权 → 调用/交付 → 计量/审计 → 复购、迭代或撤销
```

任何一步失败，都应保留失败原因和可恢复动作，不能跳过门禁后只修改前端状态。

## 3. 用户旅程

### 3.1 访客与首次进入

**目标**：快速判断 SenseMu 是否能解决自己的视觉问题。

1. 访问首页，理解四个一级入口：工作台、算法市场、数据市场、我的。
2. 在算法市场按行业、任务和采集环境筛选能力；在数据市场查看来源、许可、质量和交付边界。
3. 查看详情时只看到公开能力契约和数据卡，不看到原始对象地址、内部 manifest、密钥或租户数据。
4. 需要写入、购买或调用时进入登录入口；未登录不能通过访客头获得真实权限。

**成功出口**：登录、创建工作区、查看算法商品或查看数据卡。

**失败出口**：页面加载失败显示服务状态和重试；没有结果时提供清空筛选入口，不伪造商品。

**当前状态**：公开站点 `https://cs.sensemu.com/` 是只读演示；健康探针为 `https://cs.sensemu.com/__sensemu/health`。

### 3.2 Owner/Admin：建立协作边界

**目标**：让团队在正确工作区内生产和管理资产。

1. 创建或选择工作区，确认项目归属和当前成员角色。
2. 邀请成员；邀请令牌只显示一次，接受时需要身份提供方验证邮箱。
3. 调整角色或停用成员，所有变更追加写入权限审计。
4. 创建项目，选择任务和行业场景；项目暂停时禁止新建训练、验收、批推理、发布和工作流，但不强杀运行中任务。
5. 归档项目前检查未完成标注、视频抽帧、运行任务和在线服务；保护条件不满足时返回 `409` 和服务端原因。

**系统事实**：`Workspace`、`WorkspaceMembership`、`WorkspaceInvitation`、`AccessAuditEvent`、项目生命周期状态。

**成功出口**：工作区资源树可见，成员按最低权限开始工作。

**失败出口**：`401` 重新登录，`403` 权限不足，`409` 说明仍有受保护依赖。

### 3.3 数据生产者：从素材到冻结版本

**目标**：产出可以被训练和验收的、可复现的数据版本。

1. 创建数据集并保存类别表；类别表是唯一类别来源。
2. 创建上传意图，客户端直传图片或登记视频来源文件，再由 API 校验 SHA-256、大小和媒体类型。
3. 按训练集、验证集、测试集划分素材；未划分素材不能进入可训练版本。
4. 创建标注任务，把固定素材快照分给协作者或外部标注工具。
5. 使用编辑器或任务包导入 YOLO/COCO 标注；目标检测首期要求矩形框和类别，不要求自然语言描述。
6. 完成检查，服务端复核所有任务素材都有合法标注、类别存在且坐标在图片范围内。
7. 生成不可变 `DatasetVersion`，固化 manifest、标注、划分、类别和质量报告。

**系统事实**：`Asset`、`AnnotationTask`、`AnnotationTaskAsset`、`DatasetVersion`、`DatasetQualityReport`。

**关键门禁**：存在“标注中/待检查”任务、类别未保存、训练/验证集缺失或标注非法时，冻结接口必须拒绝。

**成功出口**：版本可被训练、验收和后续数据卡引用，历史版本不原地变化。

**失败出口**：具体显示缺失标注、类别、划分或任务状态，不能只显示“生成失败”。

### 3.4 工作区协作者：执行被分配的任务

**目标**：在不拥有商业和成员管理权限的情况下完成生产工作。

1. 通过邀请加入工作区，确认自己的 `viewer/member` 角色和项目范围。
2. `member` 可以上传素材、划分、执行标注任务、导入任务包和提交检查；不能发布服务、领取密钥或读取供应方账本。
3. 任务以固定素材快照为准，协作者不能把任务外素材写入结果。
4. 保存失败、任务撤销、权限收回或版本冻结时，页面保留服务端原因并提供返回/重试。

**成功出口**：任务进入 `completed`，数据生产者可以审核并冻结版本。

### 3.5 算法生产者：从数据到可发布模型

**目标**：把训练结果变成通过独立验收的服务，而不是只展示一条训练曲线。

1. 从已冻结数据版本创建幂等 `TrainingRun`，写入不可变任务规格。
2. Worker 领取租约，在受限 Ultralytics 容器中训练并追加进度、日志和失败原因。
3. Worker 上传真实产物：模型、`results.csv`、混淆矩阵和类别指标；API 原子登记 `ModelVersion`。
4. 选择未参与训练的独立冻结版本执行 `AcceptanceRun`，按当前版本化门禁生成逐条结论。
5. 只有验收通过的模型才能创建 `Deployment`；发布后可预热、停用和轮换 API Key。
6. 在服务设置中确认输入限制、输出协议、模型版本和环境。

**关键门禁**：训练完成不等于可发布；训练指标不能替代独立验收；失败或超时任务必须可恢复，旧租约不能回写。

**成功出口**：获得稳定的生产服务端点和可复核的验收证据。

### 3.6 算法销售者：从服务到算法商品

**目标**：把已验证能力包装成可审核、可购买、可计量的商品。

1. 从生产服务固化不可变 `CapabilitySpec`，包含问题定义、输入输出、适用边界、事件类型、交付方式、模型和验收依据。
2. 在“我的 > 创作与销售”填写标题、描述、场景、价格和额度，创建 `MarketplaceListing`。
3. 提交后商品进入 `pending_review`，不出现在公开目录，也不能下单。
4. 平台治理者审核能力契约、生产服务、验收证据和商品描述；批准进入 `published`，拒绝则保留原因。
5. 被拒商品可修改后重新提交，历史审核记录追加保留。
6. 销售者在“我的”查看订单、支付事实、成功用量和待结算收入；正式结算未开放前不显示可提现余额。

**系统事实**：`CapabilitySpec`、`MarketplaceListing`、`MarketplaceListingReview`、`MarketplaceOrder`、`PaymentEvent`、`UsageRecord`、`ProviderLedgerEntry`。

### 3.7 算法需求者：发现、购买、领取和调用

**目标**：找到能力边界清晰的算法并追踪用量。

1. 在算法市场按行业、任务和采集环境筛选，阅读适用条件、不适用条件、输入大小、输出协议和证据。
2. 选择已 `published` 商品创建待支付订单；待支付不激活额度、不计有效期、不发密钥。
3. 支付适配器验签并通过金额、币种、支付意图和幂等校验后，系统激活授权与额度。
4. 买方工作区管理员一次性领取 API Key；数据库只保存前缀和摘要，列表不返回明文密钥。
5. 使用 API Key 调用推理网关；网关先预留额度，只有成功推理才确认用量和供应方收入，失败释放预留。
6. 在“我的 > 购买与使用”查看授权期限、成功用量、订单和密钥轮换；全额退款立即撤销后续调用资格。

**失败出口**：商品下架、授权过期、余额不足、请求重复、运行时繁忙或下游超时，分别返回可处理的 `409/402/429/502/504` 语义，不扣除失败调用。

**当前边界**：公开演示不连接真实推理服务，真实购买和支付渠道尚未开放。

### 3.8 数据销售者：从冻结版本到数据卡

**目标**：在拥有分发权的前提下，把数据能力公开描述清楚。

1. 在“我的 > 创作与销售”选择自有且未公开的冻结版本。
2. 填写来源、采集方式、覆盖范围、限制、隐私处理、许可证、用途权限和权利确认。
3. 系统创建 `DataListing` 与不可变 `DataDeliverySpec`，快照绑定冻结版本和许可。
4. 数据市场展示公开卡片、质量证据和交付边界，不展示对象直链或内部清单。
5. 买方购买、授权和实际复制交付在商业合同与支付渠道接入后才开启。

**失败出口**：来源、许可证、隐私或权利信息不完整时拒绝创建；版本已公开或被删除时不能重复上架。

### 3.9 数据需求者：评估、授权和交付

**目标**：在确认用途、许可和质量后获取可用于自己工作区的数据。

1. 在数据市场按任务、行业、标注形式、规模、许可证和质量筛选。
2. 查看来源、采集方式、覆盖范围、已知限制、隐私处理、质量快照和交付方式。
3. 当前阶段只能表达需求或查看交付规范；正式开放后创建数据订单并确认买方工作区、用途和许可。
4. 支付和授权成功后，交付 Worker 按 `DataDeliverySpec` 将副本导入买方工作区，不生成原始对象直链。
5. 买方在自己的数据集内重新检查来源、标注和许可，交付记录保留版本、哈希和完成状态。

**当前边界**：数据购买、支付、复制交付、删除证明和撤销后的副本处理尚未开放，页面必须明确显示未开通。

## 4. 平台系统参与者

### 4.1 平台审核者

```text
pending_review → 读取 CapabilitySpec/Deployment/Evaluation → approved | rejected
```

审核者使用内部审核凭据，不通过浏览器接口操作。每次审核追加审核人、决定、理由和时间；拒绝后供应方可修订再提交，旧记录不覆盖。

### 4.2 支付适配器

```text
PaymentIntent → provider callback → signature verification
→ normalized PaymentEvent → entitlement activation or payment failure
```

适配器保留渠道验签所需原始字节和摘要，不把渠道字段直接写进核心领域。相同渠道事件重试必须幂等，金额或币种不一致必须拒绝。

### 4.3 Worker 与推理运行时

```text
queued task → persisted lease → execute → artifact/callback
→ success/failure → release lease and record event
```

Worker、网关和 Runtime 是受信系统参与者，不是用户角色。内部 token 不能进入浏览器；旧租约过期后禁止回写新尝试。

### 4.4 运营值班者

运营只读取 `/health/live`、`/health/ready`、`/health/operational` 和部署日志，处理训练堆积、失联任务、Webhook 失败、额度预留超时和部署异常。运营不直接修改租户业务事实，修复必须通过可审计的内部动作。

## 5. 跨角色业务链路

### 5.1 数据生产与消费

```text
数据生产者/协作者
  → Dataset + Asset + AnnotationTask
  → Review + DatasetVersion + QualityReport
数据销售者
  → DataListing + DataDeliverySpec
数据需求者
  → discovery → order/payment → entitlement
  → DeliveryJob → buyer workspace copy → delivery audit
```

不可跳过的事实：来源/许可确认、冻结版本、交付规范、授权和买方工作区边界。

### 5.2 算法生产与消费

```text
数据生产者 → DatasetVersion
算法生产者 → TrainingRun → ModelVersion → AcceptanceRun → Deployment
算法销售者 → CapabilitySpec → MarketplaceListing → Review → Published
算法需求者 → Order → Verified Payment → Entitlement/API Key
             → Gateway → Runtime → UsageRecord → Provider Ledger
```

不可跳过的事实：独立验收、能力契约、平台审核、支付验签、额度预留和成功后计量。

### 5.3 协作与权限

```text
Owner/Admin 邀请 → 身份验证 → Membership
→ viewer/member/admin/owner 操作 → AccessAuditEvent
→ 角色变更/停用即时影响后续请求
```

项目、数据集、训练、发布和商业动作均复核当前成员状态。权限收回后，侧栏和页面应清除或更新资源快照，不能继续展示可访问的历史对象。

## 6. 状态与异常语义

| 对象 | 正常状态 | 典型阻塞 | 用户可做的下一步 |
|---|---|---|---|
| 标注任务 | `draft → in_progress → review → completed` | 缺标注、类别错误、权限收回 | 修正、保存、提交检查或联系管理员 |
| 数据版本 | `candidate → frozen` | 未完成任务、缺训练/验证集 | 完成任务、补划分、重新检查 |
| 训练任务 | `queued → running → succeeded/failed/canceled` | 队列忙、租约失联、执行超时 | 等待、取消、按策略重新派发 |
| 验收任务 | `queued → running → approved/rejected` | 独立数据不合规、门禁失败 | 查看逐条原因、调整模型/门禁后重试 |
| 算法商品 | `draft → pending_review → published/rejected` | 未验收、契约不完整、审核拒绝 | 修改后重新提交 |
| 算法授权 | `pending_payment → active → expired/refunded/revoked` | 支付失败、退款、额度耗尽 | 完成支付、联系管理员或重新购买 |
| 数据交付 | `prepared_not_open → authorized → delivering → delivered/failed` | 未开放、许可不完整、复制失败 | 等待开放、补授权或重试交付 |

错误处理原则：

- `401`：身份失效，进入登录恢复。
- `403`：权限不足，不清空其他可访问资源。
- `409`：业务保护条件未满足，展示服务端原因。
- `422`：输入或数据契约不合法，指出字段或对象。
- `429`：容量或额度暂不可用，允许退避重试。
- `502/504`：下游服务失败或超时，不把请求记为成功。

## 7. 产品与后端验收标准

每条用户旅程至少要有：

1. 明确的进入条件和最低权限。
2. 一个可持久化的业务事实，而不是只更新前端状态。
3. 一个成功出口和至少一个可恢复失败出口。
4. 一个跨请求的幂等键、版本号或状态机约束。
5. 一条权限、审计或计量记录，必要时包含 request ID。
6. 演示、真实本地 API 和 staging 三种环境的边界说明。

后端新增接口前先回答：调用方是谁、对象属于哪个工作区、写入哪条事实链、失败后如何重试、是否会产生计费/交付/权限影响。答不清楚时先补业务契约或 ADR，再写路由。
